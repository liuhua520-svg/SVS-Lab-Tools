## 1. 先说清楚：这个工具要解决的是哪个问题

Synthesizer V、OpenUTAU、VOCALOID 这三款软件，出厂设定都是"歌声合成引擎"——
它们的声库是按照唱歌的发声方式采样、训练出来的，编辑器的默认交互逻辑也是围绕
"写一段旋律、配一段歌词"设计的。但虚拟歌手社区里长期存在一种更小众、但生命力
很强的玩法：不给它谱曲，而是让它像念台词一样，把一句话原原本本"说"出来——
这就是说话调教。做得好的说话调教作品，听感上跟真人配音几乎没有区别；做得不好的，
一耳朵就能听出是"在按拍子唱字"，而不是在说话。

SVS Lab Tools 的立项目的，就是把说话调教这件本来极度依赖人工、逐音符手描的
精细活，变成一条自动化流水线：**输入一段参考语音（真人录音，或者工具内置的
TTS 临时合成）和对应文本，输出一份三款软件都能直接打开播放的工程文件，虚拟歌手
打开就能把这句话"说"出来**。工具处理过程中涉及的强制对齐、音素转换、音高提取、
文件序列化这几个环节，全部是为了这一个目的服务的——尽可段忠实地把参考语音里
"这是人在说话"的证据保留下来，写进歌声引擎能读懂的数字里。

## 2. 为什么"让引擎说话"比"让引擎唱歌"难得多

这里有一个容易被忽略的反直觉之处：唱歌明明是更复杂的艺术形式，为什么让引擎
"说话"反而更难？

原因出在这些引擎的底层设计假设上。唱歌天然是**量化**的——音高被限定在十二平均
律的音阶格子上，音符时值也大致对齐拍子（四分音符、八分音符……），引擎的编辑器
和默认发音逻辑，都是围绕这套量化假设构建的。而人说话完全不是量化的：

- **音高是连续滑动的**。一句话说出口，音高可能在字与字之间不知不觉地爬升半个
  音，又在下一个字骤然回落，中间没有任何"落在哪个音符上"的概念，陈述句结尾
  下坠、疑问句结尾上扬，这些语调曲线本身就是连续的物理量，不是离散的音阶；
- **节奏是不规则的**。重读的字被拖长，虚词、语气词一带而过，同一句话不同的人
  说，甚至同一个人不同心情说，节奏都不一样，完全不讲究拍子的整齐。

如果只是把一句话的文字打进歌声引擎，让它按默认的自带 G2P（字形转发音）和默认
音高唱出来，出来的效果几乎必然是"字正腔圆、卡在整齐节拍上"——这恰恰是唱歌该有
的样子，而不是说话该有的样子。真正让人一耳朵听出"这是在说话"的，恰恰是那些不
规则、连续、极细微的音高滑动和节奏错落，而这些细节，靠人工在编辑器里一个音符
一个音符手动画出来，是极其庞大的工作量——这正是说话调教这门手艺门槛一直很高的
根本原因，也是 SVS Lab Tools 要用自动化去解决的核心问题。

## 3. 全链路总览：从一句台词到一份能"说话"的工程文件

```
参考语音（真人录音 / 工具内置 TTS 临时合成）+ 对应文本
        │
        ▼
┌─────────────────────────┐
│ ① 强制对齐               │  MFAProcessor / alt_aligners.py
│   拿到"这句话每个字什么     │  → .lab（100ns 精度的时间戳 + 音素/音节/单词标签）
│   时候说出口"的精确节奏     │
└─────────────────────────┘
        │
        ▼
┌─────────────────────────┐
│ ② 音素翻译               │  phoneme_converter.py
│   把口语里的连读、无声化    │  → ARPABET / VOCALOID4 专属记号 / 假名去母音化符号 ...
│   等含混发音如实翻译出来   │
└─────────────────────────┘
        │
        ▼
┌─────────────────────────┐
│ ③ 音高提取               │  tsubaki_processor.py + f0_extractors.py
│   提取说话本身连续滑动的   │  → 尽量保留原始语调曲线的自然形态，而非强行拉直
│   语调曲线，不强行量化     │
└─────────────────────────┘
        │
        ▼
┌─────────────────────────┐
│ ④ 工程文件序列化          │  tsubaki_processor.py
│  组装成目标引擎的文件结构  │  → .svp / .ustx / .vsqx
└─────────────────────────┘
        │
        ▼
用户在 Synthesizer V / OpenUTAU / VOCALOID4 里打开，点击播放，

```

`pipeline.py` 里的 `AudioProcessingPipeline._run_alignment()` 是①的统一入口；
如果连参考语音都没有，`tts_processor.py::synthesize_and_align()` 会先合成一段
语音再送进同一套对齐逻辑（详见第 8 节）；②③④集中在 `TsubakiProcessor` 类
（`tsubaki_processor.py`）内部顺序执行。下面逐步拆开看。

## 4. 第一步：强制对齐 —— 精确到毫秒的说话节奏

强制对齐（Forced Alignment）指的是：已知一段音频对应的完整文本内容，反推文本里
每个字/音素分别落在音频的哪个时间区间。这与"语音识别"正好相反——语音识别是不
知道说了什么、靠模型去猜；强制对齐是已经知道说了什么，只求精确的时间戳，因此
能做到比自由识别高得多的时间精度。这一点对说话调教尤其关键：说话的语速本来就
比唱歌快、且经常一带而过，时间戳但凡有几十毫秒的误差，说出来的节奏感就会明显
"不对劲"。

默认后端是 MFA（Montreal Forced Aligner），`mfa_processor.py` 里的
`MFAProcessor` 类调用其命令行工具，输出 TextGrid（词层 + 音素层），随后按语言
分别做后处理：`_process_zh_words` 按拼音音节切分，`_process_en_words` 优先用
MFA 音素层的真实时间戳、缺失时用 G2P 兜底并按音素时长权重表分配时间，
`_process_ja_words`/`_process_ko_words`/`_process_yue_words` 分别处理日语假名
音拍、韩语谚文音节、粤语 Jyutping 音节。

当用户不想装 MFA、或者需要更高精度/更快速度时，可以切换到四种替代后端
（`alt_aligners.py`）：WhisperX（词级 ASR + 对齐，免装词典）、Qwen3-ASR（中文/
多语种识别精度较高）、Qwen3-ForcedAligner（擅长长音频、中英混排）、NeMo-FA
（NVIDIA 的 CTC 强制对齐）。这四种后端产出的原始时间戳质量参差不齐，
`alt_aligners.py`（全仓最大文件，5,258 行）超过一半的代码是后处理纠错，包括
用音频 RMS 能量曲线精修静音边界避免相邻句子粘连、长音频分块时尽量让切分点落在
句子边界而不是切在发音中间、把词级时间戳进一步拆分到字符/音拍级——最后这一步
尤其重要：如果时间戳只精确到整词整句，生成出来的工程文件里只会有寥寥几个超长
音符，"说话"该有的字与字之间的节奏错落根本无从体现。

这一步最终产出统一格式的 `.lab` 文件：每行是"起始时间(100ns) 结束时间(100ns)
标签"，是后续全部步骤的共同输入——它本质上就是这句话被精确到十万分之一秒的
"说话节奏谱"。

## 5. 第二步：音素翻译 —— 把口语的含混发音也如实翻译出来

`.lab` 里的标签不是任何合成引擎能直接识别的音素记号，需要先翻译一遍，这一步在
`phoneme_converter.py`（1,832 行）里完成。这个环节对说话调教格外重要，因为口语
里大量存在连读、吞音、轻声这类现象，如果翻译时把这些含混发音"纠正"成教科书式
标准发音，说出来就会失去口语该有的松弛感，变成"念课文"而不是"说话"。

**英语**：MFA 输出的 IPA 先转成 ARPABET（`EN_IPA_TO_ARPABET`），Synthesizer V
直接使用。VOCALOID4 用自己的一套音素符号，`arpabet_to_vocaloid4()` 做进一步
转换：去重音数字、元音+尾音 `r` 合并成儿化音、词首塞音使用送气强化的"词首形式"
单独查表。整词的时间跨度会按 `distribute_arpabet_phones()` 里的音素时长权重表
细分到每个音素——双元音/长元音权重最高，塞音最短，这样切出来的每个音素时长才
符合说话时真实的长短比例，而不是简单平均分配。

**日语**：这是三种语言里跟"口语真实感"关系最直接的一支，因为它牵涉到母音無声化
（去母音化）——说快了的时候，很多音节的元音会整个"消失"，只留下一段清辅音气声，
比如"です"末尾的"す"经常并不完整发出元音"u"。这是典型的、只有说话（而不是
字正腔圆唱歌）才会自然出现的现象。`build_ja_hiragana_lab()` 会判断某个音节的
元音在这次录音里是否确实被无声化地说出来了，如果是，`ja_devoiced_onset_to_
vocaloid4()` 会查表找到 VOCALOID4 官方手册规定的专属去母音化符号（多数辅音符号
不变，但き→`k'`、ひ→`C`、ぴ→`p'`、ふ固定为`p\``），连同"锁定发音"一起写进工程
文件，这样引擎才会严格按这个真实发生过的口语现象发音，而不是自己按字面老老实实
唱出完整音节。

**中文/粤语/韩语**：分别按拼音音节、Jyutping 音节、谚文 Jamo 拆分，直接透传，
不做额外的口语化判定。

**用户自定义词典**（`dictionary_manager.py`）支持针对特定词汇做个性化发音覆盖，
但优先级排序上，去母音化这种"这一次说话确实这样说了"的客观声学事实，会排在词典
规则之前——因为它比任何静态规则都更具体、更贴近这一次录音本身发生的真实情况。

## 6. 第三步：音高提取 —— 保留说话本身连续滑动的语调，而不是把它拉直成音阶

这一步是整套流程里，跟"让引擎说话而不是唱歌"这个目标关系最直接的一环。

`AudioProcessingConfig.f0_method` 支持四种提取方式：DIO、Harvest（均基于
PyWORLD，走隔离子进程）、CREPE、RMVPE（均基于深度学习模型）。DIO/Harvest 因为
是编译好的原生扩展，在部分环境下可能触发操作系统级崩溃（Access Violation），
Python 的 `try/except` 完全无法捕获，因此 `_run_pyworld_isolated()` 把这部分
计算放进独立子进程，主进程只通过队列收结果并设超时——即使子进程被系统杀掉，也
只表现为超时提示，不会拖垮整个服务。

原始 F0 曲线要经过 `_post_process_f0()` 后处理：清除越界值、给短促静音间隙做
log2 域插值桥接、剔除可疑高频尖峰、对连续有声段做中值滤波去毛刺，再在 log2
频率域（而非线性 Hz 域）做移动平均平滑——半音本身是对数关系，log2 域平滑才不会
出现高音区过平滑、低音区欠平滑的失真，最后还有一步八度纠错，修正传统算法常见的
倍频/半频误判。

这里的关键设计取舍是：每个音符最终对应的**整数音高**（MIDI note），是取该音符
时间区间内所有有效 F0 值转换到半音空间后的**中位数**，这一步是必须的——没有
一个大致的整数音高，工程文件里的"音符"概念本身就无法成立。但真正体现"说话感"
的，是这个整数音高之外**剩下的那部分连续残差曲线**——也就是 F0 原始曲线相对
这个整数音高的偏差，这部分数据会被完整保留、写入音高曲线字段（SVP 的
`pitchDelta`、USTX 的 `pitd`、VSQX 的 Pitch Bend 控制器），而不是被舍弃或者
量化掉。正是这条连续保留下来的残差曲线，让最终播放出来的音高带着说话时真实的
起伏和滑动，而不是一条卡在整数音符上、毫无生气的直线。可以说，这一步的核心
思路始终是"尽量不把说话的语调掰整齐"，这与常规唱歌场景里往往需要把音高吸附
（Snap）到乐谱音阶上的处理方向，正好是相反的。

## 7. 第四步：工程文件序列化 —— 让三家引擎把"说话数据"当乐谱执行

三种目标格式在时间单位、音符结构、音高曲线载体上各不相同：

- **Synthesizer V（`.svp`）**：时间轴单位是 blick，`offset_ratio = bpm/60 *
  705,600,000`，LAB 的 100ns 时间戳按此系数换算成 blick 整数位置；每个音符
  `onset`/`duration`/`pitch`/`lyric`，可选 `phonemes` 字段覆盖自带发音；音高
  曲线写入 `pitchDelta`，cubic 曲线，单位 cents（= 整数音高与残差之差 ×100）；
- **OpenUTAU（`.ustx`）**：时间轴单位是 tick（480/四分音符）；日语长音符、辅音
  占位符统一规范化成 OpenUTAU 专属的延音记号 `+`；音高曲线写在
  `voice_part["curves"]` 的 `pitd` 曲线里——代码历史上这里出过真实的 bug：F0
  数据最初被误写进音符内部用于过渡效果的 `pitch.data` 字段而非 `pitd` 曲线，
  同时单位换算用了 ×1000 而不是正确的 ×100，两处都已修复；
- **VOCALOID4（`.vsqx`）**：时间轴同样是 tick；`<p lock="1">` 标签可以**强制
  锁定**手工指定的音素——如果不锁定，用户在编辑器里稍微碰一下歌词，VOCALOID
  就会按自己的词典重新生成发音，之前算出来的去母音化等口语效果会被覆盖掉，
  这也是为什么锁定机制对说话调教是刚需；音高曲线走 `<cc>` 控制器的 `P`/`S`
  双通道，`S`（Pitch Bend Sensitivity）固定写入 13 个半音，`P` 通道 ±8190 的
  整数值对应 ±13 个半音的偏差；早期版本的 PIT 曲线平滑逻辑没有按音符边界切分，
  导致相邻音符交界处出现锯齿状毛刺，后来把平滑限制在单个音符内部才解决。

三种格式虽然文件结构完全不同，但"整数音符音高怎么从 F0 中位数算出来"这套逻辑
在三处独立实现却结果一致（`_build_svp_track_payload`/`_build_ustx_track_
payload`/`_build_vsqx_part_xml`），保证同一次处理导出的三个文件，节奏感和
语调走势是一致的，只是各自遵循目标软件的文件格式约定。

## 8. 没有真人录音怎么办：内置 TTS 的"跟读"链路

说话调教最现实的一个门槛是：想要的那句台词，往往根本没有现成的真人录音可以用。
SVS Lab Tools 在这一环也做了打通——`tts_processor.py` 集成了三种语音合成引擎
（EdgeTTS、Windows SAPI、通义千问 Qwen3-TTS），并且专门提供了
`synthesize_and_align()` 这个"一次性做完"的函数：先调用 `synthesize_segments_
only()` 把台词文本合成出分句音频，再直接把这些音频交给 Qwen3-FA 强制对齐，
输出跟真人录音走完全相同格式的 WAV + LAB。也就是说，**参考语音本身也可以是
机器合成的**——用户只要打出台词文字，选一个音色，就能拿到一段带着自然语调的
临时参考语音，再把这段语音里的说话特征，原样转移到虚拟歌手的工程文件里。

这个设计直接把说话调教的门槛从"必须先找到/录到真人配音"，降低到了"打几行字就
能开始"。前端 `MFAProcessor.vue` 的"生成预览"按钮，走的是 `synthesize_
segments_only()` + `align_segments()` 两段式复用逻辑（避免用户反复点预览时
每次都重新合成一遍音频）；直接点"开始处理"则走 `synthesize_and_align()` 一步
到位。

## 9. 完整案例：一句日语台词如何变成 VOCALOID4 能"说"出来的样子

用"すき"（喜欢，口语里"す"常被去母音化）走一遍全流程：

1. **强制对齐**：MFA 对齐一段说"すき"的参考语音（无论是真人录的还是 TTS 合成
   的），`_process_ja_words` 切出两个音节区间：`s+u` 对应 0.00s–0.15s，`k+i`
   对应 0.15s–0.40s；
2. **音素翻译**：发现"す"这个音节在这次说话里确实被去母音化了（元音标注为大写
   `U`），`ja_devoiced_onset_to_vocaloid4("s","u",target="vocaloid4")` 查表
   返回只保留清辅音 `s`；"き"未被标记，按正常流程转换；
3. **写入音素字段**：VSQX 分支给"す"这个音符写入 `<p lock="1"><![CDATA[s]]>
   </p>`——只有清辅音，没有元音，锁定后 VOCALOID4 会严格发出接近气声的效果；
4. **音高**：两个音节各自的 F0 中位数换算成整数音高，F0 相对各自音符音高的
   **连续残差**写入 `<cc>` 的 `P` 控制器序列，保留这次说话原本的语调起伏；
5. **产物**：打开生成的 `.vsqx`，"す"被锁定为清辅音发音，音高带着从参考语音里
   提取出的自然起伏——虚拟歌手"说"出来的效果，会明显区别于用户自己随手打
   "すき"两个字交给 VOCALOID 默认发音引擎念出来的版本（默认引擎不知道这次说话
   里"す"被去母音化了，只会老老实实念出完整的"su"，音高也大概率会被吸附到某个
   规整的默认音符上，听起来像在念课文，而不是自然地说了一句"喜欢"）。

## 10. 对话批处理：面向配音剧/多句台词场景的批量说话生成

`DialogueBatch.vue`（前端）+ `pipeline.process_dialogue_batch()`（后端）支持
一次处理多个对话框，每个框可以是一段独立的参考语音（真人录音，或用内置 TTS
先合成一遍），处理完成后**依次背靠背拼接进同一个单音轨工程文件**：第 i 个对话
框的起始时间 = 排在它前面全部对话框真实音频时长之和，音符不会跨对话框拍平合并，
每个对话框仍是这条音轨下一段独立的序列（SVP group / USTX voice_part / VSQX
vsPart）。这个设计是专门针对配音剧、广播剧这类需要虚拟歌手连续"说"出好几句台词
的场景——如果每句台词都要单独导出成一个工程文件再手动拼接，工作量会成倍增加，
批处理把这一步也自动化了。

## 11. 这套系统的边界：它做的和不做的

**它做的**：把参考语音（真人录音或 TTS 合成）里的说话节奏、口语化发音细节、
连续的语调起伏，转换成三种格式各自能理解的显式指令（音符时间、锁定音素、音高
曲线），核心思路始终是"尽量忠实保留说话该有的样子，而不是把它规整成唱歌"。

**它不做的**：不训练、不携带、不修改任何声库，音色完全取决于用户在目标软件里
选择的声库；不做音频渲染/合成，产物永远是结构化的工程文件；也不能凭空"发明"
参考语音里不存在的语调或节奏——所有输出都是对参考素材的忠实转换，最终"像不像
在说话"的上限，取决于参考语音本身的自然程度，以及第一步强制对齐的准确度。
